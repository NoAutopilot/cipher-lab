## 1. `tools/ledger_check.py`'s own table-tracking is broken, and has been since 27-28 Sept

Running `tools/ledger_check.py` just now reports non-standard-outcome-code hits only up to line 1115 — nothing
from the other ~3180 lines of the file, even though I found 64 non-standard codes by hand in this window alone
(rows 2662-4298, all well past line 1115). Reading `check()`: it tracks `in_table` by resetting it to `False`
on *any* line that does not start with `|`, and only setting it back to `True` on a line matching
`SEPARATOR_ROW_RE` (the markdown table's own `|---|---|...|` divider). LEDGER.md has exactly **one** such
divider, at line 43, right after the header. I found **seven blank lines sitting inside the table body**, at
lines 1269, 1273, 1275, 1279, 1283, 1285 and 1287 — all between rows dated 27-28 Sept 2026 (verified with
`python3 -I -c "..."` calling `ledger_check.find_cost_index`/`split_row` directly on a current-window row,
line 4131, FAM-LINCAL, outcome `Y`: the function correctly finds the cost cell and the outcome field, so the
row-level logic is fine — it is the `in_table` state machine that never reaches it). The first blank line at
1269 sets `in_table = False`, and since no second separator row exists anywhere after line 43, it **never
becomes `True` again for the rest of the file**. Every row from line 1269 onward — 3029 of the file's 4256
data rows, including this entire week's 1637 — has been invisible to both the non-standard-outcome check and
the duplicate-session-id check this whole time, despite LEDGER.md's own header instructing every pusher to run
this tool first, and despite the tool clearly having been run plenty (its exit code and output look
superficially normal: one short list of old, pre-24-Sept findings, exit 1, nothing alarming to a quick glance).
A tool that goes quietly blind over most of its own input while still looking healthy is more dangerous than
one that errors outright. Proposal 1 fixes the state machine; proposal 2 recodes what it should have caught.
