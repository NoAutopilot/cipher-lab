## 1. `tools/intake_gate_check.py` accepted a subheading's leading word as a rule-5 status line -- thurloe-printed
   read `open` by accident until a human fix landed minutes before this session started

V8-QA6 (03:19) found `tools/intake_gate_check.py thurloe-printed` returning `open (line 15) -- ... citation found`,
but line 15 was `**Open, for the next owner (LANE W...**`, a subheading, not a rule-5 status word -- the folder had
no bare `open`/`partial`/etc. anywhere (grep for the exact rule-5 vocabulary alone on a line: 0 hits, unlike every
other pooled target touched this window). Parent 7e patched the file by hand at 03:55 UTC (a folder-level `partial`
now sits on line 2, confirmed on disk this session), which fixes this one target but leaves the checker itself able
to repeat the mistake on the next folder whose true status line is missing and a subheading happens to start with
a recognised word.

Root cause: `VERDICT_RE` matches `^[\s\-*>#]*\b(open|partial|...)\b` with no check on what follows the word on the
same line, so a markdown-bold subheading like `**Open, for the next owner...**` matches exactly as if it were a
bare status line. Checked every real NOTES.md in the repo (26 Sept 2026): no file's genuine rule-5 status line, in
its first several lines or as a `blocked (pending ...)`/`blocked -- ...` correction line (the antt-linhares-chave
shape the checker's own docstring protects), ever puts a comma directly after the verdict word -- only a
descriptive subheading does that ("Open, for the next owner", "found-solved, Bourdeau's lane" -- the latter never
reached first because its file already has a bare `found-solved` on line 1). A verdict word immediately followed
by a comma is therefore a safe, narrow signal that the line is prose about the word, not a declaration of it, and
rejecting it does not touch any of the 35 existing offline-test cases (grep-checked: none of the fixtures uses this
shape) or the `blocked (pending ...)`/`blocked -- ...` correction pattern the checker exists to catch.

```diff
--- a/tools/intake_gate_check.py
+++ b/tools/intake_gate_check.py
@@ VERDICT_RE = re.compile(
     r'^[\s\-*>#]*\b(open|partial|blocked|found-solved|solved|closed-negative|offline-only)\b',
     re.IGNORECASE,
 )
 
+def _is_heading_not_verdict(line, match_end):
+    """True when the verdict word is followed immediately (after any closing markdown emphasis
+    and whitespace) by a comma -- the shape of a descriptive subheading ('**Open, for the next
+    owner (LANE W...**', thurloe-printed's pre-26-Sept-2026 line 15) rather than a rule-5 status
+    declaration. Checked against every NOTES.md in the repo (26 Sept 2026, RETRO-2026-09-26c): no
+    real verdict line, first-line or a nearby `blocked` correction alike, puts a comma directly
+    after the word; only a subheading does."""
+    rest = line[match_end:].lstrip(" *_")
+    return rest.startswith(",")
+
+
 # Verdicts that need no citation evidence: already compliant/terminal, nothing to gate.
 TERMINAL_WORDS = ("blocked", "solved", "closed-negative", "offline-only")
```

## 5. LEARN-2026-09-26-0313's "history squashed to a 65-commit root" finding was a shallow-clone artefact, not a
   real squash -- confirmed by deepening this session's own clone

LEARN-5 (03:13) reported `git rev-list --count origin/main` = 65 and `git rev-list --max-parents=0 origin/main` =
`f2955595` (a 9,460-line diff, "effectively the entire repo state in one commit"), and treated this as a
full-repository history squash at a new scale. This session's own container was also a shallow clone (per this
brief's own header: "the container is a depth-50 clone"); running `git fetch --deepen=400 origin main` here moved
`origin/main` from 55 commits (this container's shallow count) to 470, and `git cat-file -p f2955595` shows it
does have a parent (`67e6d5188e7380762364f1df84f7271c846c37fc`) once the clone is deep enough to see it. `git
rev-list --max-parents=0` reports a shallow clone's own grafted boundary commit as a parentless root -- it cannot
distinguish "the true first commit" from "the oldest commit this clone happens to carry" -- so LEARN-5's 65-commit
root is exactly that boundary, not a squash. This is a new, more specific manifestation of CLAUDE.md rule 6's
already-documented shallow-clone gotcha (`git log --since` returning nothing across the boundary); this one is
worse because `--max-parents=0` produces a plausible-looking false positive (a real commit hash, a real diff size)
rather than an empty result, so it reads as confirmed evidence instead of an obvious gap.
