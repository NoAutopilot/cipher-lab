## 2. The near-solve staleness check now works, and it just surfaced that about half of NEAR.md is stale

Running `tools/near_check.py` with the fixed date parser flags **14 of 29 active rows** (48%) as over the
48-hour line, several by 200-400+ hours (antt-msliv0638-brochado-1712 at 385h, espagnol142-mercy-1648 at 405h,
koehler-1944 at 405h). Before the fix, this check could only see rows whose "Last touched" cell happened to
carry a clock time; now that it can read a bare date too, the backlog it was built to catch in the first place
is visible for the first time at this scale. Two things stand out:
- For several of the flagged rows (matignon-mayenne-1586, fr2933-salviati-1525, clair1161-avis-flandre-1688),
  the Evidence cell visibly contains dated sub-entries from 14-15 Oct 2026 — real, recent work — while the
  "Last touched" column the tool reads sits weeks earlier. The tool's own printed warning for these rows
  includes what looks like Evidence-cell prose running on past where "Last touched" should end, the same
  symptom (free-text prose colliding with a markdown table's column boundaries) that caused the `ledger_check.py`
  bug this retrospective found two weeks ago. I did not have budget this window to confirm whether this is a
  genuine column-shift (a stray literal `|` inside an Evidence cell, the same root cause as last time) or
  simply that "Last touched" is a separate, honestly-stale column that nobody bumps when they extend Evidence
  in place — either way, the practical effect is that half of NEAR.md's own "review every 48 hours" rule is
  not being met, and the newly-fixed checker is the only thing that now shows this.
- `near_check.py`'s check (e) (Evidence cell newer than Last-touched by more than 30 minutes) reports **zero**
  hits even on these same rows, which is suspicious given the above — if check (e) is reading the same
  possibly-shifted columns as check (c), it would miss the drift the same way; this is this week's open
  question, not a settled finding.

## 3. Three duplicate-job failures in one day, including one with an identical job name

Three `F` rows on 15 Oct 2026 — `OBRED-TRY2`, `MAT-F91`, `MAT-EYE` — all failed because they duplicated work
another account had already claimed on the same target. Two name the exact cause in their own lesson text:
"my brief error: dup check grepped ROOM for job not by section" (OBRED-TRY2) and "my brief error, dup check
grepped ROOM by job not by section" (MAT-F91). `MAT-EYE` is the sharper case: it duplicated **a job of the
same name**, `MAT-EYE`, already claimed by account 2 at 09:56 UTC that same day, and the check still missed
it — meaning even a literal job-name match is not reliably caught, let alone a differently-named job on the
same target. Three instances of the identical root cause in one day is past the point of a prose reminder.
