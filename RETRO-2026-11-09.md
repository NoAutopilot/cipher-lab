## 2. The self-scheduling mechanism that is supposed to keep a parent alive just failed the way a different one already failed once

ASKS 176's own diagnosis: the account-4 parent's next check-in was due on "an in-session cron" that depends
on that same long-running session's own `send_later`/`get_session` calls, and claude-code-remote dropped
those tools from the session before the cron fired. CLAUDE.md's Git section already documents the identical
failure *shape* for a different tool: "A long-lived orchestrator's GitHub MCP token can go stale mid-session
without an error the orchestrator notices... Route any GitHub pull-request or issue write through a
short-lived worker rather than a parent that has been running for hours." A parent's own re-arming of its
next check-in is structurally the same risk — a tool a long-lived session depends on silently stops working —
and it has now caused two consecutive multi-day stalls (61h, then 131h+) via exactly this mechanism. The fix
CLAUDE.md already wrote for GitHub tokens generalizes directly; proposal 1 below asks for that generalization
rather than a third round of ASKS-row/back-off patching for the same root cause.

## 5. Proposed changes (five; applied by nobody in this run)

**P1. Arm a parent's next check-in from a short-lived mechanism, not the long-lived parent's own session.**
Motivating evidence: section 2 — two consecutive stalls (61h, then 131h+) via the identical self-scheduling
failure, and CLAUDE.md's own GitHub-token lesson is the same shape already written down.
```diff
 Route any GitHub pull-request or issue write through a short-lived worker rather than a parent that has been
 running for hours, whether the write is a second-opinion PR close or an outreach issue post.
+A parent's own next-check-in re-arming has the identical risk and has now failed it twice (9 Nov 2026,
+RETRO-2026-11-09 P1: ASKS 176, "claude-code-remote dropped get_session/send_later" mid-session, 61h then
+131h+ silent). A parent does not call send_later on its own long-running session to schedule its next
+check-in; a short-lived dispatcher-style trigger (the kind already firing hourly for each account) re-arms
+the parent's check-in trigger instead, so the mechanism that keeps the parent alive does not depend on the
+parent's own session keeping every tool it started with.
```

**P2. A shared per-call-type pricing table, read by `brief_price_check.py` instead of restated per row.**
Motivating rows: `NEVREVOL-PREREG`, `ELEC-L29`, `NEVREVOL-ATLAS-2` (section 3).
```diff
+tools/data/call_rates.tsv (proposed): job_shape, rate, evidence, date. First three rows: opus_crop_read
+0.40 NEVREVOL-PREREG 3-Nov-2026; reconciliation_high_disagreement 2x-base NEVREVOL-ATLAS-2 3-Nov-2026;
+iiif_retune_and_read 3-units ELEC-L29 3-Nov-2026 (retune + 2 reads + a second-volume grep). A brief pricing
+one of these job shapes reads this file; a worker whose own measured rate differs by more than 20% appends
+a row rather than writing a one-off lesson sentence that the next brief-writer has to rediscover.
```

**P3. A status-word flip gates the parent's very next action on that target, mechanically.**
Motivating rows: `NEVREVOL-ATLAS`, `CHECK-WEB-3987`, `PREMISE-3987` (section 4), about USD 6 across three
jobs for one gate repair.
```diff
+**Status-flip gate (9 Nov 2026, RETRO-2026-11-09 P3).** Whenever a worker's done report changes a target's
+NOTES.md status word, the parent's next brief on that target pastes a fresh `tools/intake_gate_check.py
+<target>` run and addresses every section it names in that one brief, not the first one found — the same
+discipline Pipeline rule 2 already states, made a checklist item at the point a status word actually
+changes rather than left for the next worker's own first step to discover.
```

**P4. Keep the back-off and ASKS-row mechanism — it is working as designed.**
Not a code change: section 1 and the headline confirm RETRO-2026-11-02 P1/P2 are functioning (ASKS 176 exists
and is current; check-in interval backed off to ~2h). No further ask here except noting this plainly, since a
retrospective that only lists problems risks looking like nothing it proposes ever gets checked afterward.

**P5. ASKS.md distinguishes a platform/tool fault from an ordinary decision-needed row.**
Motivating row: ASKS 176 itself — "waiting: owner" is the same tag every other backlog item uses, but this
one cannot be resolved by the owner making a choice; it needs the owner (or whoever can) to manually restart
a session, a different kind of action than deciding a fee or answering a question.
```diff
+ASKS.md rows get an optional `blocker_kind` note (platform / decision / money / content) in the request
+column; a `platform` row (nothing in this repository can resolve it, only re-arming a session or tool access
+can) is distinguished from a `decision` row at a glance, since the two need different things from whoever
+reads ASKS.md next.
```
