## 1. Model tiering: practice has outrun the written rule, and nobody has reconciled them

CLAUDE.md's Usage item 1 still reads: "Blind searches, catalogue sweeps, harvesting, transcription passes and
any job whose output is checked by another agent run on Sonnet... Reconciliation of passes, key reading, cipher
reasoning and verifier verdicts run on the strongest model." Read literally, this window violates that
constantly: of 132 rows, only 8 (6%, USD 6.16) ran pure Sonnet 5.5; 107 (81%, USD 426.80 of USD 551.92, 77%) ran
pure Opus 5.5, and the rest mixed Opus with Sonnet-subagent reads. Sampling 25 of those Opus rows (section
title text) shows ordinary transcription/sorting work that the rule names for Sonnet: "thumbnail sweep",
"contact sheet", "sign sheet", frame-vs-frame diffs — not reconciliation or verifier verdicts. **This is not new
to my window** — RETRO-2026-10-04-acct1's own numbers for its 711-row window were even starker: Opus 5.5 638
rows / USD 2,124.2, Sonnet 5.5 only 59 rows / USD 89.7 (line 60 of that file). Before flagging this as a budget
problem, I checked whether it is a reasoned deviation: STATUS.md's results log (clair349-este-guise-1556 row)
records a measured reason — "Transcription gate passed only with Opus passes on half-line crops under 2500 px
(70.7 pct; three Sonnet pairs gave 39.3-42.0)" — i.e., for this project's specific glyph-transcription task,
Sonnet 5.5 reads crops at roughly half Opus's accuracy, a real, quantified quality gap, not an oversight. **The
problem is that this finding lives in one results-log row from weeks ago and was never folded back into the
rule it contradicts.** A fresh session reading CLAUDE.md literally (as I nearly did before checking) would
either wrongly flag the current, evidence-based practice as a violation, or — worse — follow the literal rule,
run a transcription pass on Sonnet, and reproduce the already-measured 39-42% failure. Proposal 1 below updates
the rule to state the measured exception, so it stops contradicting what the ledger shows is actually happening
for a good, citable reason.

## 2. NEAR.md: the date-only staleness gap from last week's retrospective is still open, and it just missed a second, worse case

RETRO-2026-09-28 (P3) found that `tools/near_check.py`'s `DATE_RE` requires an explicit `HH:MM`
(`r'(\d{1,2})\s+([A-Za-z]+)\.?\s*(\d{4})?[, ]+(\d{1,2}):(\d{2})'`), so a "Last touched" cell written without a

returns `None` and the row is silently skipped. That proposal was not applied (checked: `DATE_RE` is byte-

**blitz-ciphers** (78h stale) — whose Last-touched cell carries a time, "2 Oct 2026 00:19", so it parses and
correctly triggers the warning. But NEAR.md's own **untersberg-code** row reads "Last touched: 27 Sept 2026
(UNT-LANG2)" — no clock time — and is over **190 hours** (nearly 8 days) stale by the file's own 48-hour rule,
with zero warning from the tool. Last week's instance (matignon-mayenne-1586) was about a day stale when the
gap hid it; this week's instance is a week and a half stale. The gap does not self-correct — it gets worse the
longer a date-only row sits — and the fix proposed last week is a four-line regex addition that still has not
landed. Proposal 2 below repeats it with this week's confirming (and worse) example.

## 4. Board results this window used a kind ("key application") CLAUDE.md's pipeline rule doesn't name

status.json's results log shows 5 entries dated 4-5 Oct: 1 `recovery` (Hellen to Frederick II) and 4 `key
application` (three Saint-Gouard fragments under fr16104/fr16105, one Birago fragment under fr3252) — zero
`cryptanalysis`, zero `contribution`. CLAUDE.md's Pipeline section names exactly three kinds for a landed result
("a key that opened it is recovery, a reading without the key is cryptanalysis, a correction or a dataset
handed on is contribution") and Orchestrator step 3 requires "the board always carries at least one recovery
and one cryptanalysis candidate." `key application` fits none of the three by rule 7's own test — reading a
letter under an *already-published* key (Tomokiyo's, per the titles) with no new cryptanalysis and no new key

what it actually is (a reading). Whoever coined `key application` this window (it appears nowhere in the
CLAUDE.md text I was given) was reaching for a real fourth case the rule doesn't cover, not misusing an existing
one. Proposal 4 below adds it as a named fourth kind rather than leaving four of this window's five results
sitting outside the taxonomy the orchestrator is supposed to balance the board against.

**P1. CLAUDE.md Usage item 1: state the measured Sonnet-transcription quality gap instead of leaving the rule
to contradict current practice.**
Motivating rows: this window's model split (section 1); RETRO-2026-10-04-acct1 line 60 (Opus 638/Sonnet 59
rows); STATUS.md's clair349-este-guise-1556 results-log row ("70.7 pct [Opus] ... three Sonnet pairs gave

```diff

    job whose output is checked by another agent run on Sonnet (`claude-sonnet-5`). Reconciliation of passes,
    key reading, cipher reasoning and verifier verdicts run on the strongest model. The orchestrator sets the
    model when it creates the session; a worker sets it when it spawns subagents.
+   **Measured exception (5 Oct 2026, this retrospective).** Glyph/sign transcription from page crops is run on
+   the strongest model, not Sonnet, as the default for this project: a known-answer comparison on
+   clair349-este-guise-1556 found Sonnet pairs reading half-line crops at 39.3-42.0% agreement against the

+   blind catalogue sweeps, harvesting and any pass whose whole job is checked by a second independent pass
+   (check-solved, scouting) — the transcription carve-out is specific to reading glyphs off an image, not a
+   blanket upgrade.
```

**P2. `tools/near_check.py`: `DATE_RE` gets a date-only fallback (repeated from RETRO-2026-09-28 P3, still
unapplied).**
Motivating row: untersberg-code's NEAR.md entry, "Last touched: 27 Sept 2026 (UNT-LANG2)" — no clock time, ~190
hours stale, zero warning from a tool run just now; last week's instance (matignon-mayenne-1586) was about 24
hours stale under the same gap.
```diff
 DATE_RE = re.compile(r'(\d{1,2})\s+([A-Za-z]+)\.?\s*(\d{4})?[, ]+(\d{1,2}):(\d{2})')
+DATE_ONLY_RE = re.compile(r'(\d{1,2})\s+([A-Za-z]+)\.?\s*(\d{4})?\b(?!\s*[,]?\s*\d{1,2}:\d{2})')
```
`parse_dt` tries `DATE_RE` first, then `DATE_ONLY_RE`, treating a date-only match as 23:59 of that day (the
conservative direction for a staleness check — it should fire at least as often as a timed row, never less).
This is the second retrospective in a row citing this exact gap with a worse example; it is close to "broken
twice" territory for CLAUDE.md Usage 8a's own escalation rule even though the underlying tool fix was already
specified once.

Motivating rows: LEDGER.md:2612 (PIS1-KEY, archived mid-write), LEDGER.md:2618 (the lane orchestrator's own
row naming its error).
```diff
 **Verify the archive took (26 Sept 2026, RETRO-2026-09-26d).** ...closing the verification half now means the
 next hand-over is caught by a session, not by the owner noticing.
+
+**Re-check idle before archiving, not just after (5 Oct 2026, RETRO-2026-10-05, PIS1-KEY).** An idle-looking

+30 minutes earlier, losing its NOTES.md section and done line (LEDGER.md:2612/2618).
```
