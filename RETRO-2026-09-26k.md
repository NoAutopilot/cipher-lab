## Proposals (at most five; none applied)

**1. `tools/near_check.py` should flag a row whose "Last touched" precedes the newest dated mention inside its own
Evidence cell**, not only rows older than 48 hours. Motivated by malsburg-hessen-1636 above: the Evidence cell was
edited with a paragraph dated through 23:05 UTC while "Last touched" still reads 16:29 -- currently invisible to
the tool because 16:29 is well inside the 48-hour window it checks. Diff: extend `near_check.py`'s row parser to
regex-scan each Evidence cell for `\d{1,2} Sept 2026(?:,? \d{2}:\d{2})?` (or the bare-date forms it already uses
for "Last touched"), take the maximum, and add a new warning class (call it check (d), alongside the existing (a)
(b) (c)) when that maximum postdates "Last touched" by more than, say, 30 minutes -- printed as a warning like (c),
not a hard failure, since the two columns can legitimately drift by the few minutes between an edit and its own
mention. Test case: a fixture NEAR.md row whose Evidence cell contains a date-stamped paragraph one day after its
Last-touched column, expecting exit 2 (warning) not exit 0.

**2. README common tail gets one sentence: a worker whose target already carries a NEAR.md row updates that row's
Evidence and "Last touched" cells in the same push whenever its own result bears on the row's named next step or
tries a new instrument in that target's ladder.** Motivated by both matignon-mayenne-1586 (PR-LAND-9's six leads,
one of them a concrete test now running as MAT-3974, entered nowhere in the row) and fr2933-salviati-1525 (the
row's own named next step -- transcribing the plain-Italian boxes -- is 6 of 8 leaves done by SALV-PLAIN1/2, and a
tried-and-retired instrument, the wordcode context option, sits in HYPOTHESES.md and the ledger but not the
register meant to prevent exactly this kind of thing being "logged no and forgotten," the owner's own words that
created NEAR.md). Diff, in `.claude/briefs/README.md`'s common tail, after the existing "A negative's done line
carries target and control numbers side by side" sentence: "If the target has a NEAR.md row, update its Evidence
and Last-touched cells in the same push when your result bears on that row's own next step or ladder -- do not
leave it for a retrospective to notice."

**3. `tools/ledger_check.py` (or a documented convention next to it) should flag a row whose Cost cell is an
unresolved deferral** ("see the lane ledger", "parent's get_session", or any cell not matching the existing
`COST_RE`) that is still unresolved by the time a retrospective reads it. Motivated by VB-DECODE's row this window,
which still carries "parent's get_session (cap 15; 22:45-23:09 UTC)" as its literal Cost cell with no later row
anywhere in LEDGER.md pasting the actual figure -- the retrospective's own "cost per delivered result" number is a
known undercount because of it. Diff: add a `--placeholder-report` mode to `ledger_check.py` that lists every row
whose Cost cell fails `COST_RE` and whose session id is not resolved by a later row's own Cost cell (cross-checked
by session id, the same field `find_session_index`'s fallback already extracts) -- printed, not gating (a lane
orchestrator's own row legitimately says "so far" while the lane is still open), so a retrospective can run it
instead of eyeballing 35 rows by hand.

**4. Give the "stuck-rule try" its own pricing precedent, next to the other per-unit precedents in README's
common tail** ("Per-unit pricing precedents", 26 Sept 2026, LANE B9). This window's four tries ranged 3.07 to
13.03 (and VB-DECODE's cap-15, unresolved) for what the rule calls "one materially different try" -- a wide spread
because "materially different" covers both a single fresh family_run.py control pair (WC-LAGARDE2, SALV-CTX2:
about USD 3) and a multi-candidate fit loop (WC-NASSAU-FIT2: about USD 3 a candidate x 4 candidates). Diff: add one
line to the precedents section: "A stuck-rule try (README, 'one materially different try'): a single fresh
family-control pair or share-matched rerun of an existing instrument runs about USD 3 (WC-LAGARDE2, SALV-CTX2, 26
Sept 2026); a multi-candidate fit loop (several sibling keys, several key tables) runs about USD 3 a candidate
(WC-NASSAU-FIT2). Price the brief from candidate count, not a flat USD 3, when the try is a fit loop rather than a
single control pair."

**5. CLAUDE.md rule 3 gets one added sentence: a positive control demonstrating a statistical method's power must
be subsampled to the target's own event count, not run at whatever N the method's test data happens to supply.**
Motivated by ARM3-ADJ (26 Sept 2026, armstrong-madison-1808): a shorthand-run adjacency test's positive control
separated its classes cleanly at N=22,886 adjacency events, but the target has only N=28 -- "it shows the method
works, not that it has power at N=28" (the worker's own conclusion). This is a distinct failure mode from rule 3's
existing matched-negative-control paragraphs (which govern a control's *design*, N and K matching a target before
a *negative* counts); this is about a *positive* control's own sample size before it can license treating a small-N
miss as informative rather than merely underpowered. Diff, appended to CLAUDE.md rule 3 after the existing
matched-control paragraphs: "A positive control built to show a statistical method has discriminating power is
subsampled to the target's own event or sample count before that power claim licenses reading a miss on the target
as a real negative -- a method that separates two classes at N=22,886 says nothing about its power at a target's
N=28 (ARM3-ADJ, 26 Sept 2026, armstrong-madison-1808)."
